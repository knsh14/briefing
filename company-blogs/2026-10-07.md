**公開:** 2026-10-06

EmbeddingGemma 2 は、テキストに加えてコード、画像、動画、音声を共通の埋め込み空間に載せる 740M パラメータのオープンモデルで、Gemma 4 アーキテクチャをベースに Apache 2.0 で公開された。

量子化すれば Pixel 11 Pro 上でテキストのみ約 191MB、マルチモーダル全体で約 567MB の RAM で動作する。

**読む価値:** オンデバイスでマルチモーダル検索や RAG、コード検索を組むときの候補になる。

### [ReviewBench: An open benchmark for AI code review](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

## Cloudflare

### [The keys to the Internet change on October 11. Are you ready?](https://blog.cloudflare.com/root-ksk-2024-rollover/)
**公開:** 2026-10-06 | **著者:** James Godlewski

2026 年 10 月 11 日に DNS ルートの鍵署名鍵（KSK）が KSK-2017 から KSK-2024（key tag 38696）に切り替わる。史上 2 回目のロールオーバーである。
DNSSEC 検証リゾルバが新しい鍵をトラストアンカーとして信頼していないと、正常なサイトにも到達できなくなる。
RFC 5011 の自動更新には、ソフトウェアの更新やマシン移行で学習済みの状態を失う問題があり、2018 年に確認されていた。
Cloudflare は 2024 年 7 月から KSK-2024 をリゾルバに組み込み済みである。
今回は RFC 8509 の sentinel（is-ta / not-ta クエリ）を 1.1.1.1 に実装し、利用中のリゾルバが新しい鍵を信頼しているかをブラウザから確かめられるテストサイトを公開した。
アルゴリズムは引き続き RSA/SHA-256 である。

**読む価値:** 自前で DNSSEC 検証リゾルバを運用している場合は、切り替え日前に確認手順を押さえておくべき内容である。

### [How DOCA GPUNetIO Unifies GPU-Initiated Networking Across the NVIDIA Software Stack](https://developer.nvidia.com/blog/doca-gpunetio-gda-ki-unified-gpu-networking/)
**公開:** 2026-10-06 | **著者:** Elizabeth Goodman

DOCA GPUNetIO は、CUDA カーネルから Ethernet、RDMA、DMA の操作を直接実行し、CPU をクリティカルパスから外すための SDK である。
これまで NCCL、NVSHMEM、UCX/NIXL などは GPU 起点の RDMA（GDA-KI）をそれぞれ独自に実装していたが、GPUNetIO を共通基盤としてまとめ、最適化や修正を共有できるようにした。
Verbs に絞ったオープンソース版と、Ethernet や DMA まで含む DOCA SDK 版があり、オープン版は実行時に SDK を検出すると dlopen で SDK の機能を呼び出す。
プログラミングモデルは、CPU 側で転送オブジェクトを作って GPU メモリに書き出す制御パスと、CUDA スレッドが WQE を投入し doorbell を鳴らし CQE をポーリングするデータパスに分かれる。

**読む価値:** 分散学習の通信ライブラリが GPU 起点の通信をどう共通化しているかを理解する助けになる。

### [Control How Your GPU Shares Work with Green Contexts](https://developer.nvidia.com/blog/control-how-your-gpu-shares-work-with-green-contexts/)
**公開:** 2026-10-06 | **著者:** Elizabeth Goodman

Green contexts は、1 プロセス内で GPU の SM の一部とワークキューを明示的に切り出し、そこにストリームを割り当てる仕組みである。CUDA 13.1 から Runtime API でも使えるようになった。
ストリーム優先度だけでは、すでに SM 上で実行中のバルク処理のブロックを横取りできないため、レイテンシ重視のカーネルは待たされる。
SM を分割しワークキューも分けておけば、通信と GEMM の重ね合わせや Holoscan のセンサー処理のように、レイテンシ重視の小さなカーネルをすぐに開始できる。
記事では cudaGreenCtxCreate と cudaExecutionCtxStreamCreate を使うコード例と、分割の有無と優先度設定を変えた 3 モードの比較を示している。

**読む価値:** 推論やセンサー処理でレイテンシ重視のカーネルとバルク処理を同じ GPU で共存させたいときに使える手法である。

## Meta Engineering

### [NTS: Authenticated Time at Meta](https://engineering.fb.com/2026/10/06/production-engineering/nts-authenticated-time-at-meta/)
**公開:** 2026-10-06

Meta は公開時刻サービスで NTS（Network Time Security、RFC 8915）に対応し、nts.meta.com として提供を始めた。実装はオープンソースで公開している。
TLS 証明書の有効期間の上限が 2029 年に 47 日まで短縮されると、自動更新が時計のずれに左右されやすくなり、無認証の NTP では時刻が改ざんされても検知できない点が問題になる。
NTS-KE（TLS 1.3）で鍵を確立したあと、認証付きの NTPv4 で時刻を同期する。Cookie の封印鍵は共有マスターシークレットとエポックからの経過日数を HKDF に通して各サーバーが導出するため、鍵の複製もセッション表も持たない。
偽造パケットには NAK を返さず破棄し、新しい cookie を暗号化して返すことで、通信を観測してもネットワークをまたいでクライアントを追跡できない。

**読む価値:** ステートレスな鍵導出で認証付きプロトコルを水平スケールさせる設計として参考になる。

## Airbnb

### [Beyond synthetic testing: Capturing and replaying real database workloads at Airbnb](https://medium.com/airbnb-engineering/beyond-synthetic-testing-capturing-and-replaying-real-database-workloads-at-airbnb-cea7ee9b1ab2?source=rss----53c7c27702d5---4)
**公開:** 2026-10-06 | **著者:** Zuofei Wang

Airbnb は数百の MySQL 互換クラスタで本番トラフィックをキャプチャし、オフラインで再生する仕組みを作った。目的は負荷試験、容量計画、バージョンアップや移行時の互換性確認、障害の再現である。
以前は言語ごとのクライアントからクエリを Kafka に送っていたが、保守負担が大きく、トランザクションの全体像を再現できなかった。そこで全トラフィックが通る ProxySQL の組み込みクエリログを捕捉点にした。
Log Mover（サイドカーでログをオブジェクトストレージへ転送）、Log Processor（クラスタ別の分割、トランザクション内の順序復元、5 分単位のバケット化）、Log Replayer の 3 つで構成される。
auto-increment の採番差で再生結果がずれないよう、INSERT を本番で採番された ID を明示する形に書き換えている。キャプチャしたデータは本番データと同じ扱いで暗号化し、アクセスも制限している。

**読む価値:** 本番 DB トラフィックの再生で移行リスクを下げる具体的な設計と、そのトレードオフが分かる。

**公開:** 2026-10-06

Discord の定例パッチノートである。
目立つ変更は 2 つある。

**読む価値:** メディアエンジンを Rust で書き直した事例を把握する程度でよく、詳細を追う必要は薄い。

## Pinterest

### [Metrics Board: Building an Agent-ready Metrics Layer](https://medium.com/pinterest-engineering/metrics-board-building-an-agent-ready-metrics-layer-2c8fefe68756?source=rss----4c5a5f6279b6---4)
**公開:** 2026-10-06 | **著者:** Pinterest Engineering

Pinterest は、数千のメトリクスを一元管理する Metrics Board を構築した。メトリクスを一度定義すれば、計算、品質検証、公開、エージェントからの検索まで自動で処理される。
定義は Git リポジトリ上の YAML で管理する。厳密なセマンティックモデルを強制せず、任意の SQL と時間列などのメタデータを受け付ける方針を選び、UI のフォームから YAML と PR を自動生成する。
各メトリクスを独立した Airflow DAG にして、sqlglot で SQL を解析して上流データを待つタスクを自動生成し、SparkSQL か PrestoSQL にコンパイルする。
品質面ではルールベースの閾値チェックと ML による異常検知を併用し、メトリクス作成にかかる時間は数日〜数週間から 1〜2 時間に縮んだ。

**読む価値:** AI エージェントが参照できるメトリクス層を、既存のデータ基盤の上に薄く載せる設計の参考になる。

## Figma

### [3 ways product designers use the Figma agent for craft, speed, and creative expression](https://www.figma.com/blog/3-ways-product-designers-use-the-figma-agent/)
**公開:** 2026-10-06

Figma のデザインエージェントがベータを終えて一般提供になった。指示への追従と長時間タスクの処理が改善し、プロのデザイナーによる人手評価で約 60% 以上の勝率を得たという。
新機能として、ライブラリに Markdown のガイドラインを添付してデザインシステムの使い方をエージェントに伝える機能、FigJam や Slides からのコンテキスト取得、共同編集者のエージェントの作業を追う機能が加わった。
事例として、Uber はスキルを使ってコンポーネント仕様書を自動生成し、複数人で数か月かかっていた文書化を 1 人で半日に短縮した。Granola は会議メモのコネクタからフィードバックをキャンバスに注釈し、Atlassian はモーション素材をコンポーネント化してエージェントで調整している。

**読む価値:** デザインエージェントを実務に組み込んだ企業の具体的な使い方を知る材料になる。

### [Workflow lab: Staying in the flow with Figma’s agent](https://www.figma.com/blog/workflow-lab-staying-in-the-flow-with-the-figma-agent/)
**公開:** 2026-10-06

架空のアプリを題材に、デザイナーが一時的なホスト権限機能を設計する過程で、どの作業をエージェントに任せるかを示したワークフロー例である。
/repair-library-usage スキルで古いコンポーネントや変数バインディングを置き換え、判断が分かれる箇所は変更せず注釈だけを残させる。
デザインレビューのコメントを分類させて矛盾や未決事項を抽出し、セキュリティ部門が管理するチェック項目を参照する /compliance-review でフローを検査したうえで、既存コンポーネントの拡張仕様の草稿を /document-component-enhancement で作らせる。

**読む価値:** 判断を人に残し、繰り返し作業だけをエージェントに渡す線引きの具体例として参考になる。

## Vercel

### [AI Gateway adds confidence-based decision fallbacks](https://vercel.com/changelog/confidence-based-decision-fallbacks)
**公開:** 2026-10-06 | **著者:** Rohan Taneja

AI Gateway の decision リクエストで、一次モデルの回答の確信度が設定した閾値を下回ったときにフォールバックモデルへ自動で切り替えられるようになった（ベータ）。
Choice と Score の質問は confidenceBelow などの条件で、Boolean の質問は確率の範囲で判定し、複数の条件を組み合わせることもできる。
従来のエラー時フォールバックはそのまま動作する。フォールバックが発動すると 2 段階分の料金がかかる。

**読む価値:** 安価なモデルを先に使い、確信度が低いときだけ上位モデルに回す構成を手軽に組める。

## Datadog

### [Ship faster, improve reliability, and control CI costs with Datadog CI/CD Optimization](https://www.datadoghq.com/blog/ci-cd-optimization/)
**公開:** 2026-10-06

AI 支援開発で PR が増えると CI は詰まりやすくなる。
この状況に向けて、Datadog が CI/CD Optimization の機能群を紹介している。
パイプラインの実行時間とキュー待ち時間を分けて計測し、遅いジョブが Runner 不足によるものか、ジョブ自体の性能劣化によるものかを判別する。
flaky テストには自動リトライ、Early Flake Detection、PR Gates で対処し、Test Impact Analysis で変更に関係するテストだけを実行し、想定実行時間に基づく並列化でワーカー数を決める。
事例として、Betterment は平均ビルド時間を約 40 分から 10 分未満に、The Browser Company は CI 時間を 50% 短縮した。

**読む価値:** エージェントで PR が増えた後の CI 負荷にどう対処するかの観点を整理するのに使える。

### [Process and route critical security logs to Exabeam with Observability Pipelines](https://www.datadoghq.com/blog/observability-pipelines-exabeam-packs/)
**公開:** 2026-10-05

Datadog Observability Pipelines に、SIEM の Exabeam へ送るセキュリティログを送信元ごとに絞り込む Packs が追加された。
Cisco ASA、FortiGate、Palo Alto、CrowdStrike FDR、SentinelOne、Windows、Zscaler 向けに、定型ログの破棄、重複排除、サンプリングを事前に設定している。判定はパース済みのコピーや補助フィールドで行い、生のペイロードは変えないため、Exabeam のパーサーや検知ルールはそのまま動く。
全量のコピーは S3 に保存し、調査時には Replay で同じ処理を通して Exabeam に送り直せる。

**読む価値:** SIEM の取り込みコストを下げつつ検知に必要な情報を落とさないための設計例になる。
