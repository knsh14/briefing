### [Can we change an AI model’s architecture without retraining it from scratch?](https://www.amazon.science/blog/can-we-change-an-ai-models-architecture-without-retraining-it-from-scratch)
**公開:** 2026-10-12

学習済み Transformer の重みを初期値にして、attention 層の一部を state space model (SSM) 層に置き換えたハイブリッドモデルを作る手法 priming を紹介している。
SWA に置き換えたときの性能劣化を指標に変換してよい層を選び、attention の Q/K/V 射影を SSM の入力射影として再利用し、蒸留と全体のファインチューニングを行う。
必要なトークン数は元モデルの事前学習の 0.5% 未満で、Qwen、Llama、Mistral や dense と MoE の両方に適用できる。
比較では Gated KalmaNet が Gated DeltaNet と Mamba-2 を上回り、SSM はメモリ予算を 2 倍にした SWA よりも高性能だった。
32B の GKA ハイブリッドは 128K コンテキストで元モデルと同等の推論性能を保ちつつ最大 2 倍速くデコードでき、8B と 32B のモデル群、学習コード、vLLM プラグインを Apache 2.0 で公開している。

**読む価値:** ハイブリッドアーキテクチャの設計空間を低コストで比較する方法と、SSM の種類ごとの比較結果がまとまっている。

### [Impactful scheduling for GPU clusters](https://huggingface.co/blog/allenai/impactful-scheduling)
**公開:** 2026-10-09

Ai2 のインフラチームが、約 150 人の研究者が数千基の H100、B200、B300 を共有するクラスタについて、優先度ベースのスケジューラを置き換えた経緯を説明している。
旧方式では、空きの no-op ジョブで GPU を確保しておく「squatting」が起き、ほぼ全ジョブが HIGH 優先度になる優先度インフレも起きた。
新方式では、管理者がプロジェクトの木構造に沿って GPU 時間の予算を割り当て、予算で裏付けられたジョブだけをプリエンプションから保護する。
実際の割り当ては、7 日間のルックバックウィンドウで占有率を追跡する階層型フェアシェアスケジューラが担う。
GPU 配分の議論を、運用上の個別交渉から透明な予算策定プロセスへ移したことが成果として挙げられている。

**読む価値:** 需要が供給を大きく上回る GPU クラスタで、インセンティブ設計によってスケジューリングの歪みを解消した実例として参考になる。

### [Under the hood, off the hot path: How D1 scales to millions of databases](https://blog.cloudflare.com/d1-control-plane/)
**公開:** 2026-10-13 | **著者:** Lambros Petrou

SQLite ベースのサーバーレス DB である D1 を、数百万のデータベースに対応させたコントロールプレーンの設計を解説している。
D1 の稼働データベース数は 1 年で 15 倍、日次アクティブ数は 18 倍に増えており、背景にはユーザーやテナントごとに小さな DB を作る AI 支援開発の広がりがある。
各 DB は 1 つの SQLite Durable Object に対応し、クエリはエッジの Eyeball Worker から Durable Object へ直接届くため、中央のコンポーネントを経由しない。
処理をデータプレーン、中央の Postgres に依存してよいコントロールプレーン、結果整合でよい非同期プレーンに分けている。
ルーティング用メタデータは Workers KV に置き、中央 Postgres には Hyperdrive とリードレプリカ経由でアクセスするといった設計原則も示している。

**読む価値:** 大量の小規模 DB を扱うマルチテナント基盤で、ホットパスから中央依存を外す設計の具体例として参考になる。

### [Rewinding the exponential: How we keep hardware usage down](https://blog.cloudflare.com/rewinding-the-exponential/)
**公開:** 2026-10-13 | **著者:** Christian Endres

毎秒約 20 億イベントを運ぶ Cloudflare のデータパイプラインで、トラフィックの指数的な増加をハードウェア増強なしに吸収してきた施策をまとめている。
2022 年には単一の巨大スキーマを製品別スキーマに分割して基幹帯域を 35〜40% 削減し、2024 年には圧縮を LZ4 から zstd に変えて圧縮後の転送量を約 40% 減らした。
2026 年には、送信元で 2 リージョンに二重送信していた分析データを 1 回だけ送り、サンプリング後に中央側で遅延レプリケーションする方式に変えた。
この変更で広域転送が約 43 GB/s 減り、追加のリージョン間複製は約 7 GB/s にとどまった。
さらにサンプリングを送信元の Logfwdr に前倒しし、パイプライン内での集計も導入している。
5 年間の施策の合計は、ハードウェア増強を 2 年半先送りしたのに相当するという。

**読む価値:** 大規模ログパイプラインのコスト削減策が、効果の数値付きで時系列に並んでいる。

### [ReplaySSM: Rethinking State Storage for Faster Hybrid-Model Decoding](https://developer.nvidia.com/blog/replayssm-rethinking-state-storage-for-faster-hybrid-model-decoding/)
**公開:** 2026-10-12 | **著者:** Michelle Horton

ハイブリッドモデルでは、サービング時のバッチサイズで SSM 層が attention 層よりもデコードのボトルネックになることがある。
原因は、SSM の状態を毎ステップ HBM から読み書きすることと、投機的デコードで巻き戻しのたびにスナップショットが必要になることと、量子化誤差が再帰で蓄積することにある。
ReplaySSM は状態を「チェックポイントと直近の入力バッファ」で表す。
出力は毎ステップ計算しつつ、チェックポイントの書き込みはウィンドウあたり 1 回に抑える。
バッチサイズ 256 でカーネルは 1.46〜1.80 倍、デコードステップ全体は 1.20〜1.47 倍速くなり、投機的デコードの巻き戻しはバッファのポインタを動かすだけで済む。
NVIDIA と Princeton の Dao AI Lab の共同研究で、TensorRT-LLM、vLLM、FlashInfer に統合済みである。

**読む価値:** ハイブリッドモデルのサービングで SSM 層が律速になる理由と、その対処法を具体的に理解できる。

### [Shipping Media Over QUIC at Meta Scale for Instagram Live Ingest](https://engineering.fb.com/2026/10/12/video-engineering/shipping-media-over-quic-at-meta-scale-for-instagram-live-ingest/)
**公開:** 2026-10-12

Instagram Live の配信取り込み (ingest) を、約 10 年使ってきた独自プロトコル RUSH から IETF で標準化中の Media over QUIC (MoQ) に切り替えた。

判定は偽陰性を避ける方向に寄せ、中央 API から全チームが同じ分類を参照して、デプロイ速度や SLO の設定に使っている。

**読む価値:** 大量のサービスに対して、デプロイと信頼性の投資配分を決めるための重要度の定義方法として参考になる。
