### [PostgreSQL 19 Released](https://simonwillison.net/2026/Nov/19/postgresql-19/)
**公開:** 2026-11-19

PostgreSQL は例年 9 月に新版を出すが、今年は AI が報告する脆弱性への大量の対応に追われ、リリースが 2 か月遅れた。
著者が最も気に入った新機能は、読み取りをスタンバイへ送るアプリケーション向けに read-your-writes 一貫性を実現する `WAIT FOR LSN` コマンドである。
プライマリで書き込んだ後に `pg_current_wal_insert_lsn()` で LSN を取得して署名付き Cookie などに保存し、次のリクエストではスタンバイ側で `WAIT FOR LSN` を実行すると、その位置まで WAL が再生されてから読み取れる。
タイムアウトは任意で、指定した時間内にレプリカが追いつかなければエラーになる。
著者はこのパターンを Wikipedia で初めて知ったといい、Wikipedia を動かす MediaWiki は MySQL のレプリケーションに対して同じ仕組みを自前で実装している。

**読む価値:** リードレプリカを使うアプリケーションで、書き込んだ直後のデータを読み損ねない方法を探す開発者に向く。

### [Software factories and code reviews with Harjot Gill](https://newsletter.pragmaticengineer.com/p/software-factories-and-code-reviews)
**公開:** 2026-11-18 | **著者:** Gergely Orosz

AI コードレビューの CodeRabbit を率いる Harjot Gill に、AI に多額を投じる開発の進め方を聞いたポッドキャストの回である。
Gill は先月エージェントで 5,000 件を超える PR を出し、個人の AI 支出は月 25 万ドルから 27.5 万ドルほどで、PR 1 件あたり約 150 ドルになるという。
PR の多くは CI の改善や不安定なテストの修正などの雑務だが、エージェントが 6 週間動き続けて作った Rust 製の WAL は本番で稼働しており、年 1,300 万ドルの見積もりが出た CI は 1 週間で自作して見積もりの半額に抑えた。
エージェントには自分の作業を検証する手段が必要だとして、TLA+ や Lean による形式手法から決定論的シミュレーション、段階的なロールアウトまでの層を挙げている。
人がコードをレビューする時代は終わったと考えており、社内では個々の PR ではなくリリースをレビューし、障害を起こすと「strike」がたまってレビュー免除を失う仕組みを使っている。

**読む価値:** AI への支出を抑えるべきだという通説に逆らう会社の考え方や、レビューを減らしても品質を保つ仕組みを知りたい開発組織のリーダーに向く。

### [Inference engineering for software engineers](https://newsletter.pragmaticengineer.com/p/inference-engineering-for-software-engineers)
**公開:** 2026-11-17 | **著者:** Gergely Orosz

AI の費用を抑えるためにオープンモデルへ移る企業が増えているという話から始まる回で、例としてトークン単価の削減幅（Uber 50%、Pinterest 90%、AT&T 56%）を挙げる。
移行先は GPU を自前で買う方法（Revolut は B200 を 56 台運用）と推論プロバイダーの 2 つで、Modal、Fireworks AI、Baseten への取材をもとに後者を詳しく扱う。
推論プロバイダーは基盤モデルを事前学習せず、オープンウェイトのモデルを事後学習して安く提供し、効率とカスタマイズで競っている。
フロンティアラボの API の稼働率は自己申告で Anthropic が 99.5%、OpenAI が 99.97% とクラウドに期待される 99.99% に届かず、これも推論プロバイダーが顧客を得る理由になっている。
導入は既存 API を差し替えるマルチテナントの段階から始め、レート制限や性能のばらつきが目立てば専用 GPU に移り、KV キャッシュの容量やフェイルオーバー、投機的デコーディングまで検討する流れを示している。

**読む価値:** フロンティアラボの API からオープンモデルへの移行を検討するエンジニアが、推論プロバイダーの選び方と段階的な導入の道筋をつかめる。

**公開:** 2026-11-20 | **著者:** Richard MacManus

2026 年の AI 業界を象徴する言葉は低品質な出力を指す「slop」であり、AI が書くコードの slop を防ぐ手段として形式検証を取り上げた記事である。
Harmonic、Theorem、Axiom Math、新しく参入した &Truth などが AI を使った形式検証を提供しており、記事は &Truth の共同創業者で SMT ソルバー cvc5 の共同開発者でもある Clark Barrett に話を聞いている。

&Truth は Lean の上に「verification machine」を作っており、世界中の C コードがメモリ安全かを確かめるといったセキュリティ用途を重視している。

**読む価値:** AI が書くコードの正しさをテストより強く保証する方法を探す開発者が、形式検証の主な企業とそれぞれの狙いを一度に把握できる。

### [Data Contracts](https://martinfowler.com/articles/data-contracts.html)
**公開:** 2026-11-18 | **著者:** Martin Fowler

データ契約は、API 設計の手法をデータに当てはめ、データセットの内容と保証を提供者のインターフェースとして明確に記述する方法である。
保険会社のデータエンジニア Alex が、見つけたデータセットの意味や鮮度、構造の安定性、GDPR 上の扱いなどを確かめたいという例から説明を始める。
Linux Foundation の Bitol プロジェクトが管理する Open Data Contract Standard（ODCS）の YAML で、スキーマに加え、名前が空の行を 1% 未満とする SQL の品質ルールや 24 時間以内という鮮度の SLA を書く例を示している。
人はデータを疑えば手を止めて持ち主に聞くが、エージェントはすべての値を正しいものとして扱うので、データ契約で推測に頼っていたメタデータを明示すれば確信を持った誤りを減らせるという。
データ契約の性質として、機械可読で検証でき、バージョンを持ち、提供者が発行しつつ利用者に向けて書かれ、メタデータの信頼できる唯一の情報源になることを挙げている。

**読む価値:** エージェントに社内データを安全に使わせたいデータエンジニアが、データ契約の書き方と役割を具体例で学べる。

### [Deterministic Simulation Testing](https://martinfowler.com/articles/deterministic-simulation-testing.html)
**公開:** 2026-11-17 | **著者:** Martin Fowler

分散システムは部分的な障害と実際のトラフィックが重なり、同じ障害でも実行ごとに経過が変わるのでテストが難しい。
決定論的シミュレーションテストは時計、ネットワーク、ストレージをシングルスレッドの実行ループで動くシミュレーションに置き換えてすべての実行を再現可能にする手法であり、記事はクォーラム型のキーバリューストアと Java 実装 Tickloom のコードで説明する。
現実の障害は、非対称なルーティングや JVM の GC による停止、ディスクの局所的な遅延のようにきれいには壊れない「gray failure」として現れ、通常のテストではこうした状態を狙って作れない。
カオスエンジニアリングは可用性を確かめるが正しさは確かめず、Jepsen はクライアントから見た操作の履歴を検査して、書き込み成功後に古い値を読むといった一貫性の違反を見つける。
ただし稼働中のシステムでは障害の順序と実行のタイミングがどちらも非決定的なので、見つけたバグを再現できないという問題が残る。

**読む価値:** 分散システムのまれなバグを再現できずに困っているエンジニアが、決定論的シミュレーションテストの考え方を具体例でつかめる。
