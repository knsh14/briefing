## Simon Willison

### [Battle Drones - a vibe coded RTS with audio-based multiplayer](https://simonwillison.net/2026/Oct/20/battledrones/)
**公開:** 2026-10-20

Command & Conquer 風のブラウザ RTS「Battle Drones」を、コードをほとんど読まずにコーディングエージェント（主に Claude Code）で作った記録である。
12 回の大きな改版と 321 コミットを経て、3D モデル、霧の戦場、複数マップとランダム生成、AI 同士の対戦、音声で同期する近距離 2 台のマルチプレイまで実装した。
v3 までは見た目こそゲームらしいが面白くなかった。
Ultracode モード（多数のサブエージェントを動かす dynamic workflow）で「Make it a LOT more fun」と指示した v4 では、Claude が 1,000 回以上の模擬対戦を回してバランスを調整した。
その結果、25 分経っても決着しない試合は 14% から 0.9% に減り、800 スクラップ以上劣勢の側が勝つ割合は 24% から 46% に上がった。
後半の版では、AI が使わない兵種を活かす新マップを著者自身が設計して指示するなど、人間の設計関与のあり方も振り返っている。

**読む価値:**「エージェントは面白いゲームを作れない」という仮説が、長時間の自律実行と模擬プレイテストで覆された実例を知りたい人に向く。

### [What’s the ROI of software engineers’ spending on AI?](https://newsletter.pragmaticengineer.com/p/whats-the-roi-of-software-engineers)
**公開:** 2026-10-20 | **著者:** Gergely Orosz

27 社のエンジニアリングリーダーやシニアエンジニアへの聞き取りと、CodeRabbit と Gitar の集計データから、開発者 1 人あたりの AI 支出と PR 数の変化を調べた記事である。
CodeRabbit では週あたり PR 数が 1 年で 113% 増え、同じ 2 万人を追跡しても 128% 増だった。
企業規模と支出には相関がなく、2 人の .NET 企業は月 3,000 ドル/人を使う一方、エンジニア 1,500 人の上場企業は月 150 ドルに制限している。
支出は 6〜7 月にピークを迎え、Opus 5.5 やオープンモデルへの移行で API 利用者のコストはおよそ半減した。
ある量的トレーディング企業では月額支出が 1 月の 50 万ドルから 9 月には 800 万ドルに増えており、ROI はデスクの損益で判断している。

**読む価値:** 自社の AI ツール予算や上限設定を他社と比べたいエンジニアリングマネージャーに、具体的な金額と PR 数の比較材料を与える。

## Will Larson

### [Speeding up code review with `small-change`](https://lethain.com/small-changes/)
**公開:** 2026-10-17

Imprint では平均的なエンジニアの PR マージ数が 2 年で 4 倍になり、インシデントは半期比で 42%、重大インシデントは 78% 減った。
一方で PR レビューの所要時間の中央値は 33 分から 77 分に伸び、その対策として「small-change」という仕組みを導入した。
1,000 行未満、AI レビューボットの重大指摘なし、作者が対象サービスに 10 件以上のマージ実績あり、影響サービス数が上限以下、共有ライブラリを含まない、という条件を CI が判定する。
条件を満たした PR は、承認か無視の二択しか持たないレビュー用スキルで扱い、コメントは付けない。
各チームが手元のハーネスでレビューコメントを量産し、それにまたハーネスで応答する「meat proxy review」を、解決に見えて状況を悪化させるボトルネックとして批判している。

**読む価値:** AI で PR 数が急増した組織で、レビューの目的を分解し直して負荷を下げる具体策を探しているエンジニアリングリーダーに向く。

## Cal Newport

**公開:** 2026-10-19 | **著者:** Cal Newport

COLM で発表された論文「AI Assistance Reduces Persistence and Hurts Independent Performance」を紹介している。

Newport は、スマートフォンの悪影響が何年もかけて現れたのに比べ、チャットボットの影響は短時間の利用で即座に出る点が新しいと指摘する。
効果が永続的かはまだ分からないとしつつ、集中して考える力を守る使い方を自分たちで決める必要があると結んでいる。

**読む価値:** AI 支援が自力で考える力や粘り強さに与える短期的な影響を、実験結果に基づいて知りたい人に向く。

## Martin Fowler

### [When Software Meets Hardware](https://martinfowler.com/articles/software-meets-hardware.html)
**公開:** 2026-10-15 | **著者:** Martin Fowler

3,000 店舗に配備された約 80 万台の電池駆動センサーからなる小売向け IoT システムを、既存デバイスを交換せずに新しい通信技術へ移行した経験をまとめた記事である。
組込みの経験が浅いチームは、物理センサーや配線を備えた IoT ラボと、実機を新ネットワークにつないだ「sensor farm」を作り、ハードウェアを開発環境の一部として扱った。
現場で手が届かないデバイスでも状態が分かるよう、ファームウェアに診断機能を組み込み、NFC や BLE、ゲートウェイ経由で取得できるようにした。
大規模店舗で初めてネットワーク機器の接続台数の上限が判明したことから、1 台で数百台分を模擬する仮想デバイスエミュレータも作った。
高速なフィードバック、自動化、テスト、可観測性といった原則は変わらず、適用の仕方つまり「sensible default」が変わるというのが主張である。

**読む価値:** Web やクラウドの経験者が大規模なデバイス群を扱う際に、どの前提を見直すべきかを知りたい人に向く。

## Hamel Husain

### [How To Use Decision Models for Evals](https://hamel.dev/blog/posts/decision-model-evals/)
**公開:** 2026-10-20 | **著者:** Antaripa Saha

高速で安価な分類用の decision model を、LLM judge の代わりに自動評価へ使う方法を検証した記事である。
賃貸仲介エージェントの 100 件のトレースを人手でラベル付けし、Jev、Perplexity Decider、Liquid d1 と d1-ultra、Cloudflare Clef Flash、OpenAI Decisions で失敗検出の性能とコストを比べた。
既定の閾値 0.50 をそのまま使うと性能を取りこぼすため、層化 5 分割交差検証で閾値を調整する手順と、そのままコーディングエージェントに渡せるプロンプトを示している。
適合率と再現率がともに 80% 以上という条件を満たしたのは Perplexity、Liquid d1-ultra、OpenAI Decisions の 3 つだった。
Perplexity は 100 回あたり 0.82 セントで F1 0.79、OpenAI Decisions は約 4.5 倍のコストで F1 0.87 となり、スコアを確率として読めるかを確かめる較正の分析も加えている。

**読む価値:** LLM アプリの自動評価を安く回したい開発者に、閾値調整とモデル選定の具体的な手順を与える。
