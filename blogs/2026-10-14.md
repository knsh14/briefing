3.15 では PEP 810 の明示的な遅延インポート（`lazy import json`）が入り、重い依存を持つプラグインで LLM CLI の起動が数秒遅くなる問題を解消できるという。

後半では uv で 3.15 に切り替える手順と、`tomllib`、`TaskGroup`、SQLite 関連 API など、今後自分のプロジェクトで使い始める 3.11 の機能を挙げている。

**読む価値:** 複数バージョンをサポートする Python ライブラリの保守者が、3.15 の注目点と 3.11 以降に移行して得られるものを手早く把握できる。

## Kent Beck (Tidy First?)

### [Decompose Run-On Tests](https://newsletter.kentbeck.com/p/decompose-run-on-tests)
**公開:** 2026-10-13 | **著者:** Kent Beck

2013 年の記事の再掲で、セットアップのあとに操作とアサーションを何度も繰り返す「run-on test」の分解手順を説明している。
run-on test は、後半のアサーションが失敗したとき、直前の操作と前の操作のどちらが原因かわからず、デバッグの問題が残る。
探索的に設計しているとき、次のテストを既存の最大のテストに書き足してしまうことで生まれるという。
分解では、テストをコピーして最初のアサーションまでを残し、失敗時に読む人が知りたい内容を長い名前で付ける作業を最後のアサーションまで繰り返し、最後に元のテストを消す。
分割後の各テストは前段のアサーションを持たないが、スイート全体を常に一緒に実行する前提なら網羅性は元と同じだと述べている。

**読む価値:** テストコードを保守する開発者が、失敗原因を特定しやすいテストに書き直す具体的な手順を得られる。

## Martin Fowler

### [The Craft of Practitioner Voice](https://martinfowler.com/articles/practitioner-voice.html#TheCraftOfPractitionerVoice)
**公開:** 2026-10-13 | **著者:** Martin Fowler

アジャイル関連の著書を持つ寄稿者が、学術的な文章とも thought leadership とも違う「Practitioner Voice」という文章の分類を提案している。
学術的な文章は厳密さの陰に、thought leadership は体裁の陰に書き手の判断を隠し、さらに LLM の文章には責任を負う書き手がそもそもいないと論じる。
Practitioner Voice の特徴として、資格ではなく経験に基づく権威、緊張関係を解決せずに残すこと、書き手の判断を文章に残すこと、自分の経験からパターンを見いだせる読者に向けて書くことの 4 点を挙げる。
AI は Practitioner Voice の響きを真似できても、判断の結果に責任を持つことはできないとしている。

**読む価値:** 技術文書や記事を書くエンジニアが、経験に基づく文章が LLM の文章と何で区別されるかを考える材料を得られる。

### [Are Harnesses Worth the Cost?](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html)
**公開:** 2026-10-13 | **著者:** Martin Fowler

同じ API サービス（BFF）を、振る舞いハーネスの有無でコーディングエージェントに各 10 回作らせ、178 件の受け入れテストで評価した実験である。
ハーネスは、OpenAPI/AsyncAPI の仕様と例などのガイドと、契約適合性や API テストの結果を返すセンサーで構成した。
フロンティアモデルの GPT-6 Sol はハーネスなしでも 10 回すべて合格し、ハーネスありではトークンが約 10.5 倍、コストが約 7 倍に増えただけだった。
一方、低コストモデルの GPT-6 Luna はハーネスなしで 10 回中 3 回しか合格しなかったが、ハーネスありでは 10 回すべて合格し、1 回あたりのコストは Sol より 33%低かった（$0.273 対 $0.406）。
筆者は、要件が詳細に書かれた有利な条件での結果であり、要件が粗い場合にどうなるかはまだわからないと断っている。

**読む価値:** エージェント開発のコストと信頼性を設計する人が、ハーネスへの投資が効く条件を実測データで判断できる。
