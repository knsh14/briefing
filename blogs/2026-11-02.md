### [How We Took Over ChatGPT Accounts](https://simonwillison.net/2026/Oct/31/how-we-took-over-chatgpt-accounts/)
**公開:** 2026-10-31

Parameter Labs が見つけた、ChatGPT の HTML プレビュー（旧 Canvas）を悪用する攻撃を解説している。
グラフ機能で使う MathLive ライブラリの仮想キーボードが、サンドボックス内の iframe から postMessage() で呼び出せ、受信側が innerHTML を使っていたため、親ページに任意の HTML を挿入できた。
これでサンドボックス制限のない iframe を差し込み、CSP が許可していた YouTube の oEmbed エンドポイントを使って JavaScript を実行させた。
結果として、共有 URL を開いたログイン中のユーザーの個人データを持ち出したり、代わりに操作したりできた。
OpenAI は穴をふさいで 5,000 ドルのバグ報奨金を払ったが、Willison は深刻さに比べて安いと評している。

**読む価値:** サンドボックス化した iframe で利用者のコードを動かす機能を設計する開発者が、攻撃の連鎖の組み立て方を学べる。

### [AI SRE: what is it, how could it change on-call – and does it work?](https://newsletter.pragmaticengineer.com/p/ai-sre)
**公開:** 2026-10-27 | **著者:** Gergely Orosz

Rootly、incident.io、ResolveAI の 3 社に取材し、AI SRE と呼ばれるツール群の実態を整理している。
多くの企業で AI エージェントにより PR の頻度が 1 年で倍増し、Rootly のデータでは営業時間外のページがほぼ倍になったという。
インシデント率を「変更の頻度」と「1 回の変更が障害を起こす確率」の積で表し、前者が増えている以上、後者を下げる投資が必要だと説明している。

完全に自律したエージェントはまだ現実になっておらず、エンジニアに届くインシデントは減っても難しいものが残るため、スキル低下のリスクがあるとしている。

**読む価値:** オンコール体制に AI を入れるか検討している SRE やマネージャーが、現状の到達点と限界を把握できる。

## Will Larson

### [Self-reinforcing quality / adopting verification pattern](https://lethain.com/adopting-verification-pattern/)
**公開:** 2026-10-30

Imprint Engineering が、開発ループに検証パターンを取り入れた経緯と具体的なやり方を説明している。
各 PR では、ハーネスが行った検証の手順と検証できなかったことを `verifications/{pr_num}.md` に書かせ、このファイルがないと PR を draft から ready にできない。
検証できなかった箇所の一覧は、ハーネスの自走能力を高めるためのロードマップになるという。
毎日の保守工程で検証ファイルや AI レビューの採否を見直し、改善の PR や issue を自動生成しており、各コード領域は毎朝 4〜6 件の PR を受け取る。
Larson は、食い違う指示を「context poison」と呼び、重複した指示をなくして中央集権的に運用しているが、探索も続けるべきだとしている。

**読む価値:** エージェントに検証の記録を残させ、それを継続的な改善につなげたいチーム向けの具体的な手順である。

## Martin Fowler

### [Bliki: LLM Voice](https://martinfowler.com/bliki/LLM-Voice.html)
**公開:** 2026-10-29 | **著者:** Martin Fowler

LLM が書いたように感じられる文章の「LLM Voice」について、Fowler の考えを述べている。
LLM 判定ツールには懐疑的で、そもそも読み手が抱く不気味の谷のような反応こそが問題だという。
人間が手を入れても LLM Voice を消すのは難しいため、LLM に下書きを書かせるべきではないと勧めている。
書くことは考えるための道具であり、書くことを委ねれば思考や理解も委ねることになると懸念している。
一方で、パーキンソン病のために LLM を必要とする Jim Highsmith の例や翻訳のように、例外もあるとしている。

**読む価値:** 技術文書や記事を書くときに LLM をどこまで使うかを決めたい書き手に向く。
